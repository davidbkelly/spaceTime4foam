## Numerics (own derivation)

- **Edge orientation and flux.** Edges are stored as (min, max), and
  `n[edgei]` points from start to end (S3). The flux at
  `vertexCentred.C:414-418` is
  `0.5 lambda (uL + uR) - 0.5 |lambda| (uR - uL)`. For lambda > 0 this is
  lambda uL, and for lambda < 0 it is lambda uR, so it is upwind.
  `Res_j += Phi |n|` and `Res_k -= Phi |n|` give the outflow from j.
  Eq. 97 as printed gives lambda uR for lambda > 0, which is downwind.
  The comment about that typo is correct.
- **Reconstruction** (`:405-409`): uL uses grad_j and +0.5 d, and uR
  uses grad_k and -0.5 d, with d = x_k - x_j. This matches Eqs. 93-94.
  `gradient(u)` uses the computed u.
- **Weak closure** (`:198-236`):
  - Each node gets area 0.5 |n_B|.
  - The edge is inflow when A . n_B < 0.
  - The flux is the same upwind form with the interior state u_m and the
    exterior state u_b. For lambda < 0 it gives lambda u_b, and for
    lambda > 0 it gives lambda u_m, so it is consistent.
  - Corner nodes get one contribution per edge.
  - Because the form is upwind, using the exact state on outflow too
    changes nothing. Fault F6 gives bit-identical results.
- **Strong closure**: boundary nodes are not unknowns. They hold the
  exact value from initialisation, are never updated, and have their
  residual set to zero (`:429-435`).
- **Source**: `Res -= f V` (`:194`). This matches Eq. 100 with
  `div(Au) = f`. The base class gives `f = A . grad(u_exact)`, which
  matches f1 = 3(x + y), f2 = 6x + 10y and f3 = 2k exp(k(x + y)), with
  k = 0.1 by default.
- **RK2** (`:459-505`) uses Res(u*) in stage 2. On mesh 0, from the exact
  start, one step gives error 0.18142 = 0.55 (1 - g) with g = 0.67014.
  That is 1 + z + z^2/2 with z = -(0.75)(5/9), the Heun factor. Res(u^n)
  would give g = 1 + z = 0.583.
  - Both readings have the same fixed point. Fault F11 changes the norms
    by 3e-9 relative only, but takes 1190 instead of 583 iterations for
    VC-2 at N = 128.
  - Heun is the standard two-stage RK, so Res(u*) is the right reading.
- **Pseudo-time step**: D_j = sum 0.5 |n_jk . A| (Eq. 103), plus
  0.5 |n_B . A|/2 per boundary edge for weak closure. Removing that term
  (F10) changes the norms by at most 5e-10 relative. Iteration counts
  then fall slightly, for example from 583 to 577.
- **Convergence**: the RMS of Res/V over the unknowns, computed on the new
  solution. A non-finite value is fatal.

## Mesh 0 (closed form)

- V_c = 1/3, and n_c,k = (+-1, +-1)/3, so n . A = -2/3, 2/3, 0 and 0.
- LSQ at the centre: M = I, so g_c . (1, 1) = u11 - u00.
- LSQ at P00: M = [5/4 1/4; 1/4 5/4], so
  g00 . (1, 1) = (2/3)(u10 + u01 + u_c - 3 u00).
- Res_c = 0 then gives
  u_c = 0.9 u00 - 0.3 u11 + 0.2 (u10 + u01) + 0.6 f_c.
  This matches the builder and `Test-tufillaroMesh0.C`.
- u1: u_c = -0.9 + 0.4 + 1.8 = 1.3, against 0.75 exact, so the error is
  0.55 exactly. u2 gives an error of 2.0 and u3 gives 3.0971e-3; both
  match the paper.
- **"Stopped short" hypothesis.** I stopped the runs early from the exact
  start, with `endTime` n:

| n | u1 | u2 | u3 |
| --- | --- | --- | --- |
| 15 | 0.54864 | 1.99506 | 3.0895e-3 |
| 16 | 0.54909 | 1.99669 | 3.0920e-3 |

- u1 prints as 5.49e-1 only for n <= 17. u3 prints as 3.10e-3 only for

## Error measures

- The norms are weighted by V_j and normalised by the sum of the weights.
  The subsets are all, interior and boundary nodes.
- t = T: the half-edge weights sum to the length of tEnd, which is 1.
  Because the norms are normalised, only relative weights matter.
- nUnknowns is the number of nodes for weak closure and of interior nodes
  for strong.
- h = sqrt(A/(nTri/2)):
  - it is 1/N on the N x N benchmark meshes for both methods, so CCFV and
    VCFV are consistent on the same mesh;
  - it is 0.707/2^n on the Tufillaro meshes. The Table 2 script prints
    the paper's 1/2^n itself, and observed orders do not depend on a
    constant factor.
  - Not a problem for S5. The guide should state the definition when it
    quotes Table 2.
- The iteration-error check compares every norm column (CCFV 6-20,
  VCFV 6-17) as `%.3e` strings, as its header says.

| Pair | all L1/L2/Linf | int L1/L2/Linf | bnd L1/L2/Linf | T L1/L2/Linf |
| --- | --- | --- | --- | --- |
| 32-64 | 2.55/2.51/2.27 | 2.51/2.47/1.86 | 2.36/2.28/2.27 | 2.71/2.69/2.13 |
| 64-128 | 2.31/2.24/1.57 | 2.29/2.22/1.90 | 2.11/2.01/1.57 | 2.68/2.60/2.64 |
| 128-256 | 2.08/2.04/2.17 | 2.06/2.00/1.80 | 2.10/2.05/2.19 | 2.40/2.39/2.28 |

- On perturbed meshes the interior L1/L2 orders drop from 2.5 to 2.0, and
  the t = T orders drop from 2.7 to 2.4.
- On structured meshes the same orders stay at about 3.
- This is structured-mesh superconvergence. A plausible cause: on
  translation-invariant meshes the LSQ gradient is exact for quadratics
  at symmetric stencils, so leading error terms cancel. This is not
  Blocking. The slower fall at t = T on perturbed meshes (2.40 at
  128-256) is for S5 to study, with N = 512 or several seeds.
- Supporting observation: the wrong-node gradient (F3) leaves the
  structured `vcfvOrder` numbers bit-identical. That is the same
  translation invariance the `vcfvResidual` header describes.

## Test soundness

- `vcfvResidual -reference` is independent of the model. It uses its own
  Cramer's-rule LSQ, its own flux lambda, its own node loop, and its own
  weak and strong closure. Only n_jk, n_B, V_j and the edge list come
  from `medianDualMesh`, which S3 verified. The source is shared, and
  F5 and F13 are caught by T2 and LE.
- The tolerances (`100 eps |A| max|u| / h`) are sensible. Faults give
  values 1e9 or more times the tolerance.
- iterationError: confirmed above.
- stdin: `Alltest` runs each Allrun with `< /dev/null`. I ran a scratch
  copy of `vcfvSolverControl` with a fake `foamToVTK` that writes
  nothing, with stdin from an open pipe (`sleep 120 |`) and a 100 s
  guard. It exited 1 with
  `FAIL: foamToVTK writes internal.vtu (not found in run/converged/VTK)`
  and did not hang.

## Rand48

- `Rand48.H` (v2412): `operator()` returns `engine_() >> 17`, and
  `max()` is 0x7FFFFFFF, so the output has 31 bits. x = r/2^31 is exact,
  and 2x - 1 is exact (a multiple of 2^-30 in [-1, 1)). So d = m s is
  one rounded product.
- Independent C++ (`auditS4/rand/lcg2.cpp`, a hand-written 48-bit LCG,
  no OpenFOAM): (x0 + d) - x0 reproduces all ten stored values bit for
  bit, for points 64-68 at x0 = 0.125 and t0 = 0.125 to 0.625.
- `pointsChecksum` starts at the first all-digit line (the list size), so
  it leaves out the FoamFile header, the banner and the arch line. The
  test passes with `d76c6410...`.

## Minor

1. **Table 2 is report-only, so a 4x error passes T2.** In F3, T2 passed
   with relative errors up to +4.13. RS catches F3. The developer could
   consider a loose hard bound, for example 10%, which would need a
   decision on the approved "report-only" rule.
2. **The convergence measure is not checked.** F15 (Res instead of Res/V)
   passes. Its effect is below the reported digits (5.5e-7). Optionally,
   have RS check the logged residual against its own RMS of Res/V.
3. **The `tufillaroMesh.awk` comment is inexact.** It says the
   connectivity differs from crossed squares "for n >= 2". It already
   differs at n = 1: mesh 1 has the edge (0.25, 0.25)-(0.75, 0.25), which
   2 x 2 crossed squares do not. Change the comment to "n >= 1".
4. **Mesh-0 u1 gap (0.55 against 5.49e-1).** It is not explained by early
   stopping (see the table above). Record it in the guide as an
   unexplained 0.2% gap in the paper's mesh-0 u1 entry, with the closed
   form.
5. **h on the Tufillaro meshes.** `spaceTimeErrors` writes 0.707/2^n,
   while the paper uses 1/2^n. This is harmless (the script prints the
   paper's h), but the guide should say which h each table uses.
